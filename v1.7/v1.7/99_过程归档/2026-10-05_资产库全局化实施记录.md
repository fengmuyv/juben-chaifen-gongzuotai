# 2026-10-05 资产库全局化实施记录（老大反馈第 1 条）

## 一、反馈与症状

老大在使用工作台后提出四条小问题，并明确 **「一条一条改，不要同时进行」**。本条只做第 1 条：

> **1 分集这个导入的资产不通用，使用的时候一般是把所有资产全部导入，然后工作台根据描述和名称以及剧情自动选择相应集数的相应资产。**

截图证据（两条）：

- 第 03 集视图：输入图片面板 `0 张已入库`，空态；
- 第 01 集视图：同一面板 `47 张已入库 · 本段 0/6`。

即：**参考图挂在集上**，换一集就得重新导入一遍；第 03 集看不到第 01 集导入的 47 张资产。

## 二、只读核验（根因）

数据模型里资产属于集：

```ts
// src/core/model.ts（改前）
export const episodeSchema = z.object({
  ...
  images: z.array(imageSchema).default([]),
});
```

由此派生出四处连带缺陷：

1. **导入即绑定当前集** —— `store.addImages` 写的是 `activeEpisode(old).images`，`pickImages` 的重复判据也只在本集内去重；
2. **匹配结论记在图上** —— `imageSchema.matchConfidence / matchSource` 是**单值**字段。同一张主角图在 A 集唯一命中（high）、在 B 集跨 3 段需复核（medium）时，这个字段必然说谎；
3. **匹配 A 集污染 B 集** —— 模型若跨集复用同一张图，`mergeMatches` 写回的置信度会覆盖另一集的判定；
4. **重建分集要按集号搬图** —— `rebuildEpisodes` 里有一段 `imagesByIndex` 专门把图并回同号集，正是「资产归集所有」逼出来的补丁。

## 三、设计裁定

**资产归项目，匹配归集。** 两条各自单一来源，互不代偿：

| 层 | 正本 | 语义 |
|---|---|---|
| 资产库 | `project.assets`（`imageSchema[]`） | 全项目唯一一份图（含描述、确认、SHA-256、内置分析）。导入一次，全本共用 |
| 本集绑定 | `segment.imageIds` | 本集哪一段用哪几张（每段上限 6 张，沿用原约束） |
| 本集裁决 | `episode.imageMatches`（`{ [assetId]: { confidence, source } }`） | 「这张图在**本集**匹配得怎么样」——资产上没有置信度字段 |

推论（口径统一）：

- **同一张图可被多集各自绑定**（主角图本就要跨集复用），绑定是集的事；
- **匹配逐集独立**：判据是该集的说话人名册与场次名册（`buildRoster(episode)`），因此同一张图在不同集可以有不同置信度，且互不覆盖；
- **「已入库未绑定」只在「本集匹配过它却没绑上」时算问题** —— 不能拿全库资产去数（否则每集都会因为「没用到的资产」报警）。

## 四、改动清单

### 4.1 数据模型（`src/core/model.ts`）

- `projectSchema` 新增 `assets: z.array(imageSchema).default([])`；
- `imageSchema` **移除** `matchConfidence` / `matchSource`（迁到集上）；
- `episodeSchema` **移除** `images`，新增 `imageMatches: z.record(z.string(), imageMatchSchema).default({})`；
- 新增 `episodeBoundAssets(project, episode)`：本集已绑定资产的唯一投影入口。

`assets` 用 `.default([])` 而非可选：读取旧存档时缺该字段即空库，不影响解析；写入侧始终带该键。

### 4.2 存档迁移（`src/core/migrate.ts`）

新增 `hoistEpisodeImages(raw)`，**在 schema 解析之前**执行（`migrateProject` 第一行）：

- 逐集收集 `images` → 按 id 去重进 `assets`（同 id 取信息更全的一份：先比描述长度、再比版本号）；
- 每集的 `images[].matchConfidence/matchSource` 就地转成该集 `imageMatches[id]`；
- `segment.imageIds` 不动（资产 id 全局唯一，绑定关系照旧有效）；
- 幂等：已是新形态则原样返回。

**为什么必须前置**：`projectSchema` 是写入侧正本、不含 `episode.images`，zod 对未知键是**剥离**而非报错 —— 若不先搬，解析成功但整本参考图被静默抹掉，用户再保存一次即永久丢失。

v1 单集快照分支同步改造：`legacy.images` → `assets`，逐图置信度记到那唯一一集上。

### 4.3 持久化边界（`src/core/image-store.ts`）

- `detachImages` 改为剥离 `project.assets`；
- `missingImageKeys` / `attachImages` **两态都认**（`assets` 与 `episodes[].images`）—— 它们跑在 `migrateProject` 之前，此时磁盘上的旧存档尚未归一化。

### 4.4 匹配（`src/core/match.ts`）

签名由 `matchImages(episode, analyses, roster)` 改为 `matchImages(assets, episode, analyses, roster)`：**全库 × 本集**。判据与置信度分级口径一字未改，只换了「图从哪来」。

### 4.5 回填与读写入口（`src/store.ts`）

- `mergeMatches` 不再动资产，只写 `episode.imageMatches` 与段绑定；
- `addImage / addImages` 写 `project.assets`，**去重按全库 sha256**（任何一集导过的图不必再导第二遍）；
- `updateImage / confirmImage` 只重建 assets 数组 + **引用了该资产的段**（其余集保持对象引用不变，逐键编辑不吃全书浅拷贝）。

### 4.6 下游查表

`values()`（`skeleton.ts`）、`analysisFor()`（`director.ts`）、`validate()`（`validator.ts`）里的 `episode.images.find` 一律改为 `project.assets.find`；`validator` 的低置信度/未绑定两条闸门改读 `episode.imageMatches`。

### 4.7 重建分集（`src/core/planner.ts`）

- 删掉 `imagesByIndex` 那段「按集号搬图」——资产在项目级，随 `...project` 展开自然保留，重建与资产彻底解耦；
- `imageMatches` 按集号沿用；
- `hasUserContent` 改为 `project.assets.length > 0` —— **导入过资产即算用户内容**，不得自动重建。

### 4.8 界面与性能（`src/App.tsx`）

- 面板计数改「全项目资产库」（`N 张已入库 · 全本共用`），未分配区/低置信度读本集 `imageMatches`；
- 一键生成与选集生成改为 `analyzeLocal(库, 该集, …)` + `matchImages(库, 该集, …)`；
- **新增像素统计缓存**（`pixelStatsCache`，key = sha256）与 `analyzeWithStats`（`core/analyze.ts`）。
  理由：库是全局的，一次「选集生成」要为每集各判一次主体，若每次都重新解码，52 集 × 60 张 = 3000+ 次解码（单张数毫秒）纯属浪费。拆开后逐集只重算「主体 × 名册」这一半，成本与集数无关。

## 六、护栏更新（`tests/方案文档.Tests.ps1`）

原断言 `plannerBody.Contains('imagesByIndex')` 的**本意**是「重建分集不得静默丢掉用户导入的资产」。该本意不变，但实现已从「按集搬图」变为「资产在项目级、重建不碰」——断言随之改为：

```powershell
Assert-True ($plannerBody.Contains('assets.length')) '重建判据未把资产库算作用户内容（导入过资产的存档会被自动重建误伤）'
```

并新增本归档的登记断言（固化到文档契约，防回流）。

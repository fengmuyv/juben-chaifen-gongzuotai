# 导入载荷分流与乱码修复记录

## 反馈与定位

老大反馈「导入乱码」。只读取证定位到**根因不在文本编码**：

- 实测文件 `E:\资产\字字动画\倒查三代\倒查三代_全剧60集_定稿版剧本_20260930_v1.txt` 的前 4 字节为 `50 4B 03 04`（ZIP 容器魔数），包内条目为 `word/document.xml`、`word/styles.xml` 等 —— **这是一份 docx，只是被改名成 `.txt`**。
- 旧逻辑按**扩展名**判定：`.txt` → 走 `decodeScriptBytes`，严格 UTF-8 失败后回退 GB18030，把整个 zip 流解成 13.5 万字符、含 **15,565 个 U+FFFD** 的乱码灌入原稿正文。
- 同一批次的 `v1_倒查三代_全剧60集_30秒镜头表_20260930.txt` 是带 BOM 的 UTF-8，属正常文本；导入乱码与中文编码无关。

第二个静默漏洞（同批修复）：**无 BOM 的 UTF-16**。中文 UTF-16 的字节多为 `< 0x80`，严格 UTF-8 解码竟会「成功」，旧逻辑不报错、直接产出乱码。

## 改动

- `electron/text.ts`：
  - 新增 `isZipContainer` / `isCompoundDocument` / `isRichText` / `sniffScriptPayload` —— 载荷类型**只认内容魔数，不认扩展名**。
  - `decodeScriptBytes` 增加无 BOM UTF-16 判定（ASCII 半字把 `0x00` 压在固定奇偶位；要求该奇偶占比 ≥5% 且 ≥ 另一奇偶 3 倍，二进制随机 `0x00` 不对称会被挡住）。
  - 新增解码后二进制体检 `assertReadableText`：替换符 + 控制字符 + NUL 占比 > 0.5% 即报中文错误，不再把乱码当正文。
  - 旧版 `.doc`（OLE2）、RTF 直接给出可执行的中文提示。
- `electron/main.ts`：`script:open` 按 `sniffScriptPayload(bytes)` 分流，回传 `kind: 'docx' | 'text'`；对话框放宽到 `txt/md/json/docx/doc/rtf`，让旧格式能被选中并得到明确提示而非「文件不可见」。
- `src/App.tsx`：浏览器路径同样按魔数分流（与主进程**同一判据**）；`.md` 说明文档闸门只在 `kind === 'text'` 时生效。
- `src/core/word.ts`：非 docx 压缩包给出明确中文错误，替代解析器原始异常。
- `src/vite-env.d.ts`：`window.workbench.open()` 返回值补 `kind`。

## 验证

- 真文件端到端（重建后的真实模块 + 真实伪装件）：`sniffScriptPayload = docx`，解析正文 113,497 字符、**替换符 0**、首行 `《开局扮演鬼子扫荡，全网直呼倒查三代》`。
- 新增单测：按魔数分流（伪装 `.txt` 的 docx → `readWord` 可读）、无 BOM UTF-16 正确解码、旧版 `.doc` / RTF 明确报错、二进制载荷被拦截。
- 新增 e2e：以 `.txt` 名称与 `text/plain` MIME 送入 docx 字节，断言原剧本编辑区出现正文且不含 U+FFFD。
- `npx tsc --noEmit`、`npm run build:desktop`、`npm test`（81 项）、`npm run test:docs`、`npm run test:e2e` 全绿。

## 剩余边界

- 纯汉字、不含任何 ASCII、且无 BOM 的 UTF-16 仍无法可靠识别（无判别特征），此类文件请另存为 UTF-8 或带 BOM 的 UTF-16。
- Big5 / Shift-JIS 等非 GB18030 繁体或日文编码不在支持范围，GB18030 兜底会产出「能解码但语意错误」的文本，需要显式编码选择器才能根治。
- `src/core/text.js`、`shared/text.js` 为已失效模块的编译副本（真实使用 `electron/text.ts`），仍待批准清理。

# 「道具」图类退役与资产下拉改造实施记录（2026-10-06）

> 来源：老大两张截图 + 原话 —— 「自动读取资产中上传的人物」「把左边的输入图片改为**下拉选择人物，场景**；**道具选区不要了**」。
> 四轮追问后的落定：① 删除道具 + 改下拉；② 道具**连数据层一起退役**；③ 老存档里的道具资产**直接丢弃**；
> ④ 下拉形态 = **下拉 + 已选标签**；⑤ 交付节奏 = **分两步走**（本轮 = 第一步）。
> 第二步（自动读取人物 → 按人物生成「人物设定 / 人物弧光」文本框，先只落盘）**未在本轮做**。

## 一、决策表

| 决策点 | 裁定 |
|---|---|
| 「道具」的边界 | **连数据层一起退役**（不是只从界面拿掉） |
| 老存档里的道具资产 | **直接丢弃**（不搬迁、不改判为人物或场景） |
| 输入图片的新形态 | **两类各一组「下拉 + 已选标签」**；从下拉里点一张即绑定本段，也是描述编辑对象 |
| 描述编辑区 | **一次只开一张**（选中项）；原「每张卡一个编辑区 + 用于本段勾选」取消 |
| 判不出图类时 | 返回 `null`，**不硬塞一个类目**（硬塞会误入自动匹配） |
| 丢弃的可见性 | **可以丢，但不许静默丢** —— 张数上报到界面提示条 |

## 二、为什么必须「解析前归一化」（本轮最关键的一条）

道具退役是一次**结构性 schema 失配**（structural，非容忍性）：`imageSchema.kind` 的枚举从三类收成两类。
这**不是** `projectSchemaTolerant` 能治的那种问题 —— 那一跳只放宽「版本指纹」两个字段，枚举本身仍是 strict 的。

后果链条：

1. 老存档里只要有一张 `kind: 'prop'`；
2. → `projectSchema.safeParse` 失败（enum 不匹配）；
3. → `projectSchemaTolerant.safeParse` **同样失败**（它只放宽版本指纹，不放宽枚举）；
4. → `v1ProjectSchema.parse` 也失败；
5. → `loadDraft` 把「解析失败」吞成「无存档」→ 用户看到的是一份**空工作台**。

也就是说：**不做任何事**，用户的整份存档（含导演板全部内容）会**静默消失**。这比「道具资产没了」严重得多。

故在解析**之前**插一步 `retirePropAssets`（`src/core/migrate.ts`）：

- 逐条过滤 `assets`，摘掉 `kind === 'prop'` 的条目并记 id；
- 同时把这些 id 从**每一集每一段**的 `segment.imageIds` 里清掉（否则会留下指向不存在资产的悬挂引用）；
- 顺手把 `analysis.kindGuess === 'prop'` 归一为 `null`（老存档里由旧版 `classifyKind` 写下的兜底值）；
- **幂等**：没有道具资产、也没有待归一的 `kindGuess` 时原样返回（`raw` 引用不变），不做无谓改写。

调用点在 `migrateProject` 里紧跟 `hoistEpisodeImages(raw)` 之后：`const retired = retirePropAssets(hoistEpisodeImages(raw));`。
顺序不能反 —— 先归一化再解析，是这段代码存在的全部理由。

## 四、界面改造要点（`.asset-picker` 一组）

- **下拉**（`aria-label="选择人物参考图"` / `选择场景参考图`）：选项 = 本类全部资产（空描述的标「（未写描述）」）；
  选中即调 `pickForSegment` → 先 `setEditing`，再 `toggleImage(segment.id, image.id)`；
  到 6 张上限时**只提示不改数据**（「该图保留在库中标记为已入库未绑定」）。
- **已选标签**（`aria-label="本段已选人物"`）：名字是「在下方编辑」的入口（`.chip-pick`），
  × 只解除本段绑定（`.chip-drop`），资产仍在库中。
- **单开编辑区**（`.asset-editor`）：缩略图 + 名称/来源行 + 色卡 + 描述框 + 三键。
  空描述时一行提示「未写描述：这张图不会进入 ① ②」——注意**已去掉 ④**（道具退役后 ④ 不再吃描述）。
- **组内四键**：`一键补充描述` / `一键补充 AI 描述` / `清空描述` / `清空本类全部资产`（语义与位置沿用上一版）。

## 六、边界与未做

- **不搬迁**：老存档里的道具资产按裁定**直接丢弃**，不尝试重新归类。理由：硬塞成人物或场景会让他**误入自动匹配**，
  比丢掉更坏（用户会在 ①② 里看到一张本不该在那儿、且图类错误的图）。
- **第二步未做**：自动读取资产中已上传的人物 → 为每个人物生成「人物设定」「人物弧光」文本框（**先只落盘、不接 AI 请求**）。
  其中「自动读取人物」的口径已定为**只读派生**（从现有名册 / 资产派生，不新增可手工编辑的名册），
  详见下一份归档。
- **随附取舍未答**：`CastPane` 的「确认设定」按钮判据（`project.visual.confirmed` 那一套）是否要跟着改 ——
  因人物锚点将变为只读派生。该问题本轮**未落定**，随第二步一并裁定。

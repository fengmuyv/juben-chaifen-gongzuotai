# 解析口径对账实施记录（2026-10-05）

> 主题：**「改了识别口径，打开还是没变」** —— 分集结果是持久化的，旧存档不会自己重算。
> 一并收掉上一轮挂起的启动卡顿候选 A / C / D。

## 一、反馈与症状

老大在 `15440c0`（Markdown 井号集标修复）之后打开工作台，反馈 **「没变啊」**，并附截图：
《猫大夫的快乐处方》仍是 **「第01集 / 491 段 / 24098 项阻断」**。

直觉是「代码改了、重开就该好」——但事实并非如此，下面给出核验。

## 二、只读核验：为什么「没变」

| 项 | 核验结果 |
| --- | --- |
| 修复是否在源码 | ✅ `src/core/parser.ts` 命中 `15440c0` 改动（`(?:#{1,6}\s+)?`） |
| 构建是否含修复 | ✅ `dist/`（00:33）晚于 `parser.ts`（00:30） |
| 修复是否有效 | ✅ 上一轮用同一份样例实测：修复后 **2 集 / 325 项阻断** |
| `hydrate()` 是否重解析 | ❌ **不重解析**（`src/store.ts` 只做「读存档 → 恢复」） |

**根因**：分集结果是**持久化**的 —— 导入那一刻由解析器切好、写进 IndexedDB。
之后升级识别口径，**已存在的存档不会重算**；用户打开看到的仍是旧分集，且**没有任何提示**。
这是一个静默的不一致：用户不可能知道「改了解析口径要手动重建」。

**责任**：上一轮只交了修复、没交代「存量存档需要重建」，属交付漏项。

## 三、方案 A：解析口径对账（根治）

四处改动，全部单源：

1. **版本指纹单源** = `src/core/parser.ts` 的 `export const parserVersion`。
   规矩写进注释：凡改动 `episodeCapture` / `episodeHeadingOf` / `preludeOf` / `isSceneHeading` /
   `headingKindOf` / 说话人与名册判定，**必须 bump** —— 否则对账不触发，修复等于没交付。
2. **存档字段** = `projectSchema.parserVersion: z.string().optional()`。
   刻意可选：旧存档读到 `undefined` 即「旧口径」；不用 `z.literal`（那会让读旧存档 strict 失败，
   而 `projectSchema` 是写入侧正本，不该为读取方便放宽）。
3. **对账单一来源** = `src/core/planner.ts`：
   - `reconcileSplit(project)` → `current` / `rebuilt` / `stale` 三态；
   - `hasUserContent(project)` → 「可否自动重建」的唯一安全判据（原稿版本 / 视觉设定 / 参考图 /
     人工确认 / 生成痕迹 / 锁定镜头 / 导演板字段，逐项任一为真即**不自动重建**）；
   - `rebuildEpisodes(project)` → 重建单一来源，用户主动的 `replan()` 与自动对账**共用**。
4. **接入** = `src/store.ts` 的 `hydrate()`：读到存档即对账；
   `rebuilt` 时**立即落盘**（否则用户直接关窗，下次打开又得重算一遍）；
   `stale` 时一个字段都不动。结果经 `splitStatus` 交给界面 —— **对账绝不静默**。

**顺手修掉一个既有隐患**：`rebuildEpisodes` 原逻辑（即原 `replan`）会把 `episode.images` 一起清空 ——
用户导入的参考图会**静默丢失**。现按集号把原图并回重建后的同号集；集号在重建后消失的并入首集
（宁可多留，不静默丢）。段级 `imageIds` 会因段重建而失效，图片本体与描述完整保留。

## 四、卡顿 A：参考图与主存档分离

**问题**：整个项目（含内嵌 `dataUrl`）被一次性 `JSON.stringify` 写入 IndexedDB；
69.8MB 快照实测 **250ms**，且每次自动保存都要重来一遍 —— 而图片字节几乎从不变化。

**改法**（拆装正本 `src/core/image-store.ts` + 落盘 `src/core/storage.ts`）：

- **内容寻址**：key = `image.sha256`（schema 本就有），图片单独存 `images` store（`dbVersion` 1 → 2）；
- **只写新增**：保存时先 `getAllKeys()` 比对，已存在的 sha256 不重写；
- **顺序固定：先图后主** —— 中途失败最多丢掉主 JSON 的本次更新，
  绝不会出现「主 JSON 引用了还不存在的图」；
- **装不回就显式失败**：剥离态把 `dataUrl` 置**空串**（不是删字段），schema 的
  `startsWith('data:image/')` 会当场挡住 → `migrateProject` 报错 → `loadDraft` 返回 `failed`
  （界面提示、且不覆盖原档）。**绝不给一个空 `dataUrl` 的坏图。**
- localStorage 兜底**不剥离**（没有第二个 store，且 5MB 配额本就撑不起参考图）。

## 五、卡顿 C：`updateScript` 不再追加整本全文

**问题**：`updateScript` 此前无条件 `push` 一整本全文 —— 每点一次「保存原稿版本」存档就线性膨胀，
而每次自动保存都要把这个膨胀后的存档整体 `JSON.stringify`。

**改法**：文本未变 → 直接 return；文本与某个既有版本一致 → 切回该版本，不造重复副本。

## 六、卡顿 D：载入占位

**问题**（只读核验发现）：`src/App.tsx` **完全没用 `storageReady`** —— 载入期间直接渲染
「从原剧本开始」的空工作台，用户会以为存档丢了。

**改法**：`!storageReady` 时渲染载入占位（`Loader2` 旋转 + `aria-busy`）；
超过 1.2s 补一句「这份存档较大，正在装回参考图并重建分集」—— 小项目一闪而过，不啰嗦。

## 七、附带修复：e2e 一个用例都没跑就失败（残留产物撞宿主护栏）

**症状**：`npm run test:e2e` 直接报
`Error: [safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":792,"threshold":50,"targets":["E:\\剧本拆分工作台\\test-results"]}`。

**根因**：Playwright 每次运行都清空 `outputDir`，而本项目 **teardown 会挂死**（已知现象），中断后留下数百个残留文件；
下一次运行时那批批量删除就撞上宿主环境护栏。**这不是产品缺陷，是环境坑**（`环境约束.md` 有前科）。

**改法**：新增 `scripts/prepare-e2e.mjs`，跑测试前把残留目录**整体 `renameSync` 移走**
（移走 ≠ 删除，不触发护栏），落点 = 工作区同级的 `wb_temp/`（非 C 盘、非同步区），并接进 `test:e2e` 脚本。
契约加三条断言锁住：脚本存在、已接入 `test:e2e`、**必须用 `renameSync`**（防止有人换回删除）。

**顺带修**：e2e 里 `indexedDB.open('script-storyboard-workbench', 1)` **硬编码了库版本** ——
本轮 `dbVersion` 升到 2，用旧版本打开高版本库会抛 `VersionError`。已改为**不指定版本**（跟随应用当前版本）。

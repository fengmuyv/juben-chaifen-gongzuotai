## 0. 定性与边界

### 0.1 这是 U，不是 D

| | D（重做） | **U（本方案）** |
|---|---|---|
| 数据模型 | 重设计 | **不动** |
| 持久化 | 换存储 | **不动**（IndexedDB 已定案） |
| 解析层 | 重写 | **不动** |
| 本地引擎判据 | 重写 | **只换来源**（硬编码 → skill 包），判据本身不改 |
| 校验 / 导出 / 匹配 | 重做 | **不动** |
| AI 通道 | 重做 | **不动**（`ai-client.ts` 已是唯一出口） |
| 14 格骨架 | 改 | **不动**（编号、顺序、标签一个不改） |

本方案做的**只有三件事**：① 判据从源码里搬到 skill 包并能被运行时读取；② 把本地 / AI 两个引擎的边界与适配写清；③ 界面按「一具壳 + 两个引擎」重排并同构。

### 0.2 七项已确认的裁定

1. **P ≡ 段（Segment）**，15 秒一段。界面加一层 P 编号（P01、P02…），选中 P 载入其 SC；**不改数据模型**，`planner` 切出的 groups 即 P。
2. **① 人物 / ② 场景 = 资产描述的自动带出位**，由系统按人物名册与场次自动识别，**无人工动作、无按钮、无快照语义**（必为引用：改资产描述即改分镜 ①②）。
3. **Skill 走运行时读取**（非构建期编译）：内存缓存 + mtime/hash 失效，本集元数据记 `{ skillId, version, hash }`。
4. **UI 以最后定稿为准**（2026-10-05）：资产区采用 **三框并列**（人物 / 场景 / 道具），推翻同日上午中间态的「单入口 + 弹出小框」。既有 `asset-kind-menu` / `activeAssetKind` 相关断言**随之删改**。
   - **2026-10-06 再推翻**（老大原话「把左边的输入图片改为**下拉选择人物，场景**；**道具选区不要了**」）：三框并列改为**两类各一组「下拉 + 已选标签」**，且「道具」图类**连数据层一起退役**（§5.2-3 已改写）。本条的**去向**保留在此仅为留痕 —— 它记录的是 10-05 那一版定稿，不再是生效口径。
5. **资产线与剧本线互通**（2026-10-05）：两条业务线**分开呈现**，但**数据层共享同一个连接键（人名 / 场景名）**，不是各存一份、互不相干的孤立面板 —— 详见 §5.4。
6. **首版只做短剧**（2026-10-05）：剧型路由包一律不装载；**`contentTypes` 枚举保持不动**（改会让存量存档 strict 失败），界面不提供剧型选择 —— 实现面几乎为零，`planner.ts:145` 新建项目本就固定 `contentType: 'short-drama'`。
7. **只装 MiniMax 专项包**（2026-10-05）：唯一可见入口 = `minimax-h3-video-prompt`，其余三个依赖包由 manifest 的 `dependencies` 自动解析装载，**用户视角只有一个包** —— 详见 §2.5。

### 0.3 当前实证（开工前基线）

| 项 | 事实 | 证据 |
|---|---|---|
| 主进程读盘能力 | **已有**，与 AI 无关 | `electron/credentials.ts:91` 读 `.env.local`；`electron/main.ts:88` 读导入剧本 |
| AI 唯一出口 | 纯网络，**不读文件** | `electron/ai-client.ts:11-13` 明文「不读 .env、不写文件」 |
| skill 包目录 | **不存在** | 全盘扫描 `resources/` 零结果 |
| 运行时读 skill | **明确不做** | `director.ts:10-11`「技能不在运行时读取」 |
| AI 侧规则来源 | **硬编码 10 条常量** | `electron/script.ts:35-49` |
| 本地侧规则来源 | **硬编码查表** | `src/platforms/minimax-h3/rules.ts`（27 条禁词） |
| 双写根因 | 主进程无法 import 渲染层 | `tsconfig.electron.json` 的 `rootDir: "electron"` |
| 溯源锚 | **缺失** | `director.ts:20` 自认「暂无来源版本与 SHA-256 锚」 |

**结论**：AI 端现在**已经在消费 skill 的内容**，只是消费的是「编译进源码的手抄副本」——无版本号、无 hash、改 skill 不会跟随。本方案要做的，是把「手抄副本」换成「可从包里读取的正本」。

┌─ 执行层 ─▼──────────────┐   ┌────────▼──────────────┐
│ 本地引擎（渲染层）        │   │ AI 引擎（主进程）      │
│ src/platforms/minimax-h3 │   │ electron/script.ts    │
│   rules / director /     │   │ electron/vision.ts    │
│   skeleton / validator / │   │   ↓ 拼 system prompt   │
│   audit / gate / repair  │   │ electron/ai-client.ts │
│   （查表 · 确定性）        │   │   ↓ HTTPS             │
│                          │   │ LLM API（生成性）      │
└──────────┬───────────────┘   └────────┬──────────────┘
           │                            │
┌─ 编排层 ─▼────────────────────────────▼──────────────┐

### 2.2 `meta.json`（manifest，扩技术方案 §8 L224）

```json
{
  "id": "ai-manhua-storyboard-qa",
  "version": "1.6.0",
  "apiVersion": "1",
  "dependencies": [],
  "sourceSha256": "<SKILL.md 全文的 SHA-256>",
  "sourcePath": "C:/Users/win10/.workbuddy/skills/ai-manhua-storyboard-qa/SKILL.md",
  "capabilities": ["h3.validate", "transition.guard"],
  "consumers": { "local": ["rules.json"], "ai": ["prompt.md"] }

```

- `sourceSha256` **解决 `director.ts:20` 的「无锚」**：从此可跑对账脚本发现漂移。

- `consumers` 声明本包对两路各供什么，加载器据此挑段、不整包塞给 AI（省 token）。

### 2.4 `SKILL.md` 与 `prompt.md`

- `SKILL.md`：**人读正本**，保留上游技能原文（含方法学、示例、判据出处），`sourceSha256` 对它计算。
- `prompt.md`：**AI 段**，由 `SKILL.md` 提炼的可直接拼进 system 的结构化条款（即 `script.ts:35-49` 那 10 条的规范形态，但**带出处、带版本**）。

> 老大裁定的「用了就行」= **双段式**（人读 + 机读同源，一份正本两种消费）。

### 2.5 首版装载范围（2026-10-05 裁定：只做短剧 · 只装 MiniMax 专项）

**唯一入口 = `minimax-h3-video-prompt`。** 其余四个是它的 `dependencies`，由加载器按 manifest 自动解析装载 —— **用户视角只有一个包**，界面上不单独列出、不可单独禁用、随入口一起启用或回滚。

| 包 | 角色 | capabilities |
|---|---|---|
| **`minimax-h3-video-prompt`** | **入口（唯一可见）** | `h3.compile` `h3.validate` |
| └ `ai-manhua-director-thinking` | 依赖 · 导演意图锚 | `director.intent` `staging.anchor` |
| └ `ai-manhua-emotion-clip` | 依赖 · 情绪档 × 强度 | `emotion.design` |
| └ `ai-manhua-storyboard-qa` | 依赖 · 交付闸门 | `transition.guard` |
| └ `ai-manhua-screenplay-comprehensive` | 依赖 · 14 字段骨架正本 | `skeleton.fields` |

**为什么物理上分开、逻辑上只有一个入口**：这四份内容是**四个不同知识域**（平台编译 / 导演意图 / 表演情绪 / 交付质检），单独成包才能各自独立更新与回滚；而用户不需要知道它们的存在。这正是技术方案 §8 `dependencies` 机制的设计意图 —— `minimax-h3-video-prompt@2.1.0` 的 manifest 本已登记 `ai-manhua-director-thinking@^3.8.0`、`ai-manhua-storyboard-qa@^1.5.0`。

**不装载**：全部剧型路由包（`short-drama-factory` / `mid-drama` / `long-drama` / `film` / `deepwhite-shotlist-builder` / `design-fight-videos`）。理由有两层：① 首版**只做短剧**；② 技术方案 §8 L200 明确「这些模块只生成或校验通用导演中间数据，**不能输出 H3 的 14 字段正文**」，当前链路用不上。

> **若你要更彻底（一个物理包）**：把这四份内容全部并进 `minimax-h3-video-prompt` 的 `rules.json`（§2.3 按 capability 分节本就是为此设计），目录里只剩一个包。代价是导演意图 / 情绪档 / 交付闸门三者**失去独立更新与回滚能力**，改一处要整包换版。**默认按「一个入口 + 四个依赖」实现**，加载器两种形态都能读 —— 要合并说一声即可。

## 4. 双引擎分治

### 4.1 三层划分（「规则类似但要适配」的落地）

| 层 | 内容 | 归属 |
|---|---|---|
| **L0 判据正本** | 转场禁词 27 条 / 台词零改动 / 14 格必填 / 时长不变量 / 越轴 / beat 覆盖 | skill 包 (2.3)，两路共用，**不得双写** |
| **L1 生成策略** | 何时取证、何时设计、⑭ 如何选型、上下文给多少 | 各引擎适配层 |
| **L2 执行体** | 本地 = 查表；AI = 自由生成 | `director.ts` / `script.ts` |

### 4.2 七项适配（逐条）

1. **⑩⑪⑬ 条件覆盖**：`mergeDrafts` 现**无条件**用本地结果覆盖 AI 结果（`store.ts:176`、`L200`）。改为按 `draft.source` 与条目 tier 四态（本地生成 / AI 生成 / 人工改过 / 空）分流。
2. **prompt 第 7/8/9 条改口径**：现要求「照抄 beatText，无证据填无」；AI 应改为「原稿证据优先，无证据时按情绪档 × 弧光强度设计，仅空镜填无」——与本地口径对齐。
3. **⑭ 选型 vs 创作**：本地从 `positivePool` 选型（确定性）；AI 可自拟，但**必须过 L0 禁词闸门 + 写明匹配元素**。
4. **③⑤⑥ 不查表**：AI 侧不得套本地 `shotTemplates` 档位表，须按 grade 语义自行判断（口径由 prompt 给出）。
5. **上下文不截断**：AI 请求带**本集原文 + 上段完整结果**（现 `L181-185` 只带当前段）。
6. **人物设定 / 弧光消费**：AI 侧 prompt 加「人物设定与弧光」段。**2026-10-06 订正**：本地引擎并非「不消费」—— `skeleton.values()` 在无资产描述时会把它作为 ① ② 的文字兜底（`文字设定：…`）、`validator` 的 `VISUAL_UNCONFIRMED` 与相邻段锚点漂移比对也取它；本地界面只是**不提供录入入口**（该段仅 AI 态渲染）。已有锚点的老项目切到本地照常生效，故**刻意不做数据侧收口**（删回落会让老存档导出产物里的 ① ② 一起变空）。
7. **人名防幻觉（AI 侧独有）**：返回的 ⑨/⑫ 人物名**必须落在 `projectCast()` 名册内**，否则该镜退回本地结果——本地引擎无此项（它从名册取名，不会造名）。
8. **改写边界的修订（2026-10-06 · 老大报「AI 推理后与本地一键生成一模一样」后定）**：上面七项落地后仍留着一个**结构性**缺口 —— `mergeDrafts` 的逐字段写入受顶栏「覆盖已有内容」开关约束（未勾选即「只补空白」），而板上只要已按本地规则生成过一次（**任何一次导出**都会经 `prepareForExport` 用本地规则把整集填满），AI 出稿的每一条字段都会被逐条 `continue` 跳过 ⇒ **AI 一个字都没落盘**，「一模一样」既是观感也是事实。修订为**按草稿来源分侧**：`draft.source === 'ai'` 不受该开关约束（可覆盖 `local` / `ai` 两种既有值），唯一不可越过的是**人** —— `locked` 与 `draftSource === 'manual'` 的镜头生成通道一律不改写；本地草稿沿用原语义。两条配套：① ④ 构图与 ⑨ 站位的同源校正**排除 AI 草稿**（冲突交给闸门 `audit` 的 `STAGING_COMPOSITION_CONFLICT` 报出，回填层不再替 AI 做证据收敛）；② `GenerationResult` 新增 `protectedShots`，0 条写入时界面据此说清「为什么没写」，而不是报一句会误导的「校验通过」。
9. **失败必须说得出原因（2026-10-06 同轮）**：AI 路径的 `catch` 原为**空捕获**，`describeNetworkError` 又只取 `error.message`（undici 在网络层失败时恒为 `fetch failed`），于是「4 段全回退本地」这类结果**不带任何原因** —— 老大无从区分是密钥、地址还是网络。修订为：`describeNetworkError` 带出最内层 `cause` 的 `code` + `hostname:port`（仍过 `redact()` + 截断 160 字），编排层逐段收集失败原因去重后进提示条（`errorNote` / `failureNoteOf`）。本次实测即由此定位到真因：`UND_ERR_CONNECT_TIMEOUT`，目标为所配置的上游接口地址。

### 4.3 双写的消灭

`rules.ts` 与 `script.ts` 各持一份 27 条禁词，靠 `workbench.test.ts` 一致性断言兜底。加载器就位后**两侧都从 skill 包读**，双写与那条护栏断言**同步退役**（改为「两侧读同一 `rules.json`」的正向断言）。

## 5. UI 施工清单

左栏两条业务线——**剧本原稿**（解析侧）与**资产**（素材侧）——**分开呈现但数据互通**（§5.4）；右栏是二者的汇合产物（分镜）。注意这两条线与「本地 / AI 两个引擎」是**正交**的两个维度：引擎决定「谁生成 ③–⑭」，业务线决定「① ② 从哪来」。

### 5.1 一具壳 + 两个引擎

### 5.4 资产线 × 剧本线的互通（2026-10-05 老大裁定）

两条业务线在界面上分开呈现，但在数据层**共享同一个连接键：人名 / 场景名**。互通不是新增机制，而是把已有链路在界面上显式化。

**三条通道**

| # | 方向 | 机制 | 代码正本 | 界面落点 |
|---|---|---|---|---|
| ① **需求** | 剧本 → 资产 | 集内名册 = 可信说话人 + 场次标题关键词 | `match.buildRoster(episode)` → `characters` / `scenes[].keywords`；全本口径用 `director.projectCast(project)` | 资产框顶部「**剧本需 12 人 · 已有 9 · 缺 3**」 |
| ② **供给** | 资产 → 剧本 | 逐集匹配结论 + 段级绑定 | `episode.imageMatches`（置信度 / 依据）+ `segment.imageIds` | 资产卡状态标：**本集命中 / 全本命中 / 未分配** |
| ③ **注入** | 资产 → 分镜 | 描述进 ① ② | `skeleton.values()`：按 `segment.imageIds` 筛 `kind` 取 `description`（两类：`character` → ①、`scene` → ②）。**2026-10-06「道具」图类退役后，④ 构图不再拼接道具描述**，回归「只写导演的构图」 | 审阅台 ① ② 格（只读，标「资产」） |

**双向定位（互通的界面形态）**

- 点剧本侧某个人名（名册 / 分集清单）→ 资产侧对应人物卡高亮；缺图则**就地提示「未导入」**。
- 点资产卡 → 列出引用它的集与段（`imageMatches` + `segment.imageIds` 反查）。

**两条铁律**

1. **两侧不得各存一份人物 / 场景实体**。剧本侧只出「名册」（从原文解析、**只读派生**），资产侧只出「资产」（`project.assets` 项目级单源），中间靠名字对齐。名册不可在界面上手工编辑——要改就改原稿，否则「改一次名册，分集对账（`reconcileSplit`）会把它冲掉」。
2. **匹配永不静默丢弃**：未命中进「未分配区」（`confidence: low`），超额段登记 `overflow`（`match.ts:58-59`）。界面必须把「缺」显式说出来，不让用户误以为资产已齐。

> **本项目已具备这三条通道的全部代码**（`match.ts` / `model.ts` 的 `imageMatches` / `skeleton.ts` 的 `values`）——互通要做的只是**把它们在界面上露出来**，不加新数据、不加新存储。

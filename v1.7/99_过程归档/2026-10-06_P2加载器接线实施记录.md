## 1. P2 的准确范围

方案 §7 给 P2 的验收判据是两条：**拆掉包目录仍能跑（降级）**、**包内 hash 改一位即报错**。
两条都在本文件 §5 有实测证据。

本期只做「**读取与对账**」，**不做「切换供源」** —— 生效判据仍取自
`src/platforms/minimax-h3/skill-default.ts` 的内置默认包，磁盘包读进来但不参与生成。
这不是缩水，是刻意的分期：**「加载器接线」与「本地判据改由磁盘包供给」是两件事**，
把它们并在一期，P2 的「行为零变化」就只能靠「包内容恰好没漂移」来保证（脆弱），
而不是靠结构保证（可靠）。切换与双写退役一并归 P3。

### 为什么这条分期是必要的（一个真实风险）

`resources/skills/**/SKILL.md` 参与 SHA-256 溯源锚校验。若在 P2 就切供源，
那么**任何一次上游技能更新备份到 `resources/skills/`**，都会立刻改变产品行为 ——
而 P2 的验收判据「零变化」就再也测不出来。先把闸门立稳、把对账断言按死，切换才是可控动作。

### 分层纪律（与 `credentials.ts` 同一条）

`manager.ts` **不 import `electron`**：落点由调用方以 `bases` 传入（开发态 `app.getAppPath()`、
打包态 `process.resourcesPath`、`cwd` 兜底），模块内只做「在给定根里按序找包」。好处是单测能直接
import 并指向任意目录，**不需要起 Electron**。

## 3. 三个需要说清的取舍

### 3.1 `catalog.json` 的条目里没有 `apiVersion`（实测踩到）

第一版把条目 schema 写成 `skillMetaSchema.extend({ path })`，装载时 5 个包**全部报
`apiVersion: Invalid input: expected "1"`**。真因不是 zod，而是**上一轮打包脚本产出的
`catalog.json` 条目里本来就没有 `apiVersion`** —— 协议版本由顶层统一声明一次，
条目只带索引所需字段（`id` / `version` / `domain` / `entry` / `dependencies` /
`sourceSha256` / `capabilities` / `path`）。

修法不是「给条目补字段」，而是**把条目定义成索引条目**（不含 `apiVersion` / `sourcePath` /
`consumers`），并让 `catalog.json` 与 `scanCatalog` **共用同一个构造器 `indexEntryOf`** ——
两个来源的「同构」于是由代码保证，而不是靠约定（约定会在某次只改一边时静默分叉）。

### 3.2 完整性校验只认**原始字节**，不做换行规范化

实测 5 个包的 `SKILL.md` 原始字节哈希与 `meta.json` 的 `sourceSha256` **全部一致**，
所以不存在「必须规范化才匹配」的情况。反过来，规范化**会出问题**：
`ai-manhua-storyboard-qa` 与 `ai-manhua-screenplay-comprehensive` 的上游正本是 **CRLF**
（另 3 个是 LF），规范化后哈希变成另一串 —— 于是「被改了一位」与「只是换行风格不同」
再也无法区分。故只认原始字节，换行稳定性交给 `.gitattributes` 锁死。

### 3.3 降级锚 `'builtin'` 而不是伪造一串 SHA-256

`builtinStamp.hash` 固定为 `'builtin'`。内置默认包没有与之对应的 `SKILL.md` 全文，
算不出真哈希；**伪造一串十六进制会让「内置包」与「真实包」在界面与日志里无法区分**，
那正是溯源锚要解决的问题的反面。`skillStamp()` 因此可以直接用「hash 是不是 `builtin`」
回答「我的包到底生效了没有」。

## 4. 三个非显然的坑（都已最小复现，都写进了代码注释）

### 4.1 `fs.cpSync(src, dest, { recursive: true })` 会崩掉整个 vitest worker

| 探针 | 结果 |
|---|---|
| import `manager` + `loadCatalog` | ✅ 通过 |
| `cpSync` **非递归**（单文件） | ✅ 通过 |
| `cpSync` **`recursive: true`** | ❌ worker 退出码 **3221226505（`0xC0000409` / STATUS_STACK_BUFFER_OVERRUN）** |
| 自写浅层 `copyTree`（逐层 mkdir + copyFile） | ✅ 通过（21 个文件 / 297K，2.1 秒） |

症状极具误导性：测试文件被**正常收集**（`Tests (22)`），却一个用例都跑不完，且 Node
**不抛任何 JS 异常** —— 只有 `[vitest-pool]: Worker forks emitted error`。

### 4.2 宿主 safe-delete 垫片会让「测试里删临时目录」失败

宿主（WorkBuddy CLI）对 `node:fs` 挂了垫片：递归 `rmSync` 被改写成「移入回收站」流程，
在临时目录上以 `Error during a trash operation: Some operations were aborted` 抛错 →
**22 个用例全绿，却仍报 1 个 Failed Suite**。改成逐项 `unlinkSync` / `rmdirSync` 后
不再报错，但**慢到 10 秒 hook 超时**（整轮 28 秒）。

最终方案：**测试里一个删除动作都不做** —— 固定 fixture（`<仓库>/.workbuddy/temp/skill-fixtures/`，
已被 `.gitignore` 忽略）、每次 `beforeAll` 把正确内容**重写**一遍（幂等）、用例只做「再改一位」
这类**写**动作；需要「目录不存在」的场景直接用**不存在的路径**表达，不必先建再删。
结果：**28 项 / 58ms / 零残留**。

### 4.3 `Omit<SkillCatalogEntry, …>` 会被 zod 的 `.loose()` 索引签名污染

`SkillCatalogEntry` 出自 `.loose()` 的 zod schema，带 `[key: string]: unknown`。
对它做 `Omit` 之后，`id`、`version` 这些**具体键会一起退化成 `unknown`**（TS 报
「`unknown` 不能赋给 `string`」）。修法：显式写出参数类型，不用 `Omit`。

### 附注：P1 轮 e2e 的结论只作参考（如实记录）

P1 那一轮的 e2e 同样是 **25/25 通过（EXIT=0）**，但其运行期间 `electron/script.ts`
正被本期的改造改到半途，vite 热重载报过一次

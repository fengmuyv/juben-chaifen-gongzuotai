## 二、诊断（改造前）

- 「无法保存」的真相：桌面端链路本就完整，工程根 `.env.local` 里**确实已有** `WORKBENCH_API_KEY` 三行 —— 写入是成功的。缺的是**可见性**：
  ① 密钥按设计永不回显，保存后输入框依旧空白 → 看起来像失败；
  ② 本机存过 key 后输入框为空 → 「保存到本机」按钮变灰**点不动**，想再点也点不了。
- 按钮 UI 不随 AI 就绪变化：`aiReady` 当时只影响按钮的 `title`（悬停才可见）与面板里一行小字，两个按钮的 `className` / 文案 / 图标**恒定不变**。

## 三、实施

### 1. 密钥填入即自动常驻（`src/App.tsx`）

- 删除「保存到本机」按钮与 `saveKeyToLocal()`，**不新增任何按钮**。
- 新增自动写入 effect：**800ms 防抖**，靠三条边界保证正确：
  - **`keyTouched` 闸门** —— 初始为空（用户没动过）一律不写。少这道闸门，一打开设置面板就会把本机已配置的密钥抹掉。
  - **清空即撤销** —— 空串是合法入参，语义为「从本机删除」，对应老大说的「我主动把他删了」。
  - **成功不弹提示** —— 逐键刷屏比没提示更糟；结果只落在「本机密钥状态」一行。
- 输入框占位符：本机已配置且输入框为空时显示 `••••••••••（本机已保存，留空即用它）` —— **不回显明文**，但一眼能看出「它一直在」。

### 2. 凭据落点锚定（`electron/main.ts` + `electron/credentials.ts`）

- 成因：`credentialsStatus()` / `saveLocalCredentials()` 默认用 `process.cwd()`。从不同目录启动（快捷方式、打包产物）会让 `cwd` 漂移，出现「写过一次、重开就没了」——写与读落在两个不同目录。
- 改为**锚定应用自身**并合成查找链：主进程新增 `credentialsDirs(): string[]` —— 开发态 = `app.getAppPath()`（工程目录，用户可见可手工编辑）；打包态 = `app.getPath('userData')`；`process.cwd()` 退为兜底。`credentials:status` 与 `credentials:save` 两处 IPC 都改用它。
- `loadLocalCredentials` 支持**多目录非空合并**：某一处只写了地址、另一处写了密钥时两边都生效；`saveLocalCredentials` 只写查找链**首项**，读取走完整链条，保证「写哪儿读哪儿」不分裂。

### 3. 生成按钮随 AI 就绪换形态（`src/App.tsx` + `src/styles.css`）

- AI 就绪：「一键生成」→ `Bot` 图标 + **「AI 依次推理」**文案 + `.ai-ready` 强调态（紫色，与 `来源：AI` 同一色系）。
- **`aria-label="一键生成"` 锁住可访问名** —— 可见文案随状态变，而既有 e2e 的 `getByRole('button', { name: '一键生成' })` 全部继续有效。
- 新增 `data-ai="ready|local"` 供机器断言；「当前生成主路径」那行同步变紫。

### 4. 「全部分集生成」→「选择集生成」（`src/App.tsx`）

- 语义重复的根因：「一键生成」在 AI 就绪时已是逐段依次推理，「全部分集生成」也是逐集逐段同样的事，等于同一功能两个入口。
- 改为**选集浮层**：`openPicker()` → 分集勾选网格（复用闸门浮层外壳）+ 「全选 / 全不选 / 只选当前集」快捷 + 底部「生成选中的 N 集」。
  - **默认只勾当前集** —— 「补跑一集」是高频诉求，不该先逼用户「全不选」。
  - 勾选后 `generateEpisodes(episodeIds)` 按**工程集序**（非勾选顺序）处理，保证 AI 依次推理的上下文链与剧集顺序一致。
  - 全选即等价于原来的「全部分集生成」，功能不丢。
- 文案口径：`全部分集生成完成` → **`选集生成完成`**。

### 5. 启动路径：折叠态不再整本解析（`src/App.tsx`）

- 原 `const split = useMemo(() => sourceText ? splitEpisodes(sourceText) : null, [sourceText])` 属**无条件整本解析**，只服务折叠清单里的标题/字数/行号 —— 违反既有纪律「折叠态既不渲染 DOM 也不计算」。
- 改为 `splitOpen && sourceText` 门控；面板上那句「已自动识别 N 集」改由 `project.episodes.length` 判据给出，不再依赖解析结果。

## 五、启动卡顿：第一轮定位（**结论已被 §七 取代 —— 本节的测量口径有误，真因在渲染层**）

> 保留原文以留痕。**请以 §七 为准**：本轮把「元素出现」当可交互，漏掉了提交帧里的解码成本，
> 因此把归因过多地压在了「读写解析大存档」上。

**已定位**：卡顿不由 JS 计算主导。带图存档实测「首屏可交互 3650ms / JS 长任务仅 448ms」——其中约 3.2 秒花在**非阻塞的读写与解码**上：

1. IndexedDB 读取整份大存档（55MB 字符串的结构化克隆）；
2. `JSON.parse` 整份存档；
3. `migrateProject` 的 zod 全量校验（字符串本身是引用传递，成本低于预期）；
4. 首屏把当前集参考图全部 base64 解码上屏。

**根因**：参考图以 base64 **内嵌在主存档同一条记录**里。这同时放大了三条链路 ——
打开（读 + parse + 校验全量）、**每次自动保存**（`JSON.stringify` 全量 + 写全量，55MB 量级下每次数百毫秒到秒级）、以及内存占用。

**候选优化（按性价比排序，均需老大批准后另立一轮）**：
- **A. 参考图与主存档分离**：图片按 `id` 单独存一个 object store，主存档只留引用。一次性解决打开与每次保存两条链路，是全量问题里收益最大的一条（改动涉及 `storage.ts` 存档结构与 `imageSchema` 落盘口径，需迁移兼容）。
- **B. 导入时压缩参考图**：**核对后作废** —— `prepareImage`（`src/core/images.ts`）**早已在做**：长边限 1024、`canvas.toDataURL('image/jpeg', 0.74)`。此条系我未先读代码就列出的错误候选。
- **C. 存档瘦身**：`updateScript` 每次「保存原稿版本」追加一份**全文**，反复迭代会累积多份整本原稿，直接放大存档与每次序列化成本；可改为只保留最近 N 份或按需裁剪。
- **D. 打开期间给出可见进度**：即便优化到位，大存档仍需时间；兜底做法是在 hydrate 期间显示「正在载入存档（N MB）」，避免用户面对无响应的白屏。

> 已保留两条长期护栏用例：`有存档时打开不卡顿`、`带参考图的存档打开不卡顿`，各打印真实数字并设宽松阈值，专门拦「回到卡死」的回归。

## 七、第二轮（同日 · 老大复报「打开后还是会卡住」）：口径修正与真因修复

### 7.1 我的测量口径是错的

老大复报原话：**「打开后还是会卡住，鼠标放在按键 UI 上大概三秒后才有反应」**。

回看，§五 那份结论建立在一个**错误判据**上：e2e 用 `expect(locator).toHaveCount(n)` 判「首屏可交互」——
**元素进了 DOM ≠ 主线程空闲**。参考图的解码发生在节点出现**之后**（更准确地说，在 React 的提交帧里），
那段时间 hover 完全没反应。旧口径两头都漏：既截断了 DOM 之后的阻塞，又漏掉了提交帧里的解码。

### 7.2 先分离数据层：数据层根本凑不出三秒

新增一个隔离基准（临时探针，跑完已删），构造 **52 集 / 6240 镜 / 208 张图** 的真实形状工程：

| 层 | 2.1MB（无图） | **69.8MB（带图）** |
| --- | --- | --- |
| `JSON.stringify`（**每次自动保存都跑**） | 11.2ms | **250.1ms** |
| `JSON.parse`（打开） | 9.2ms | 89.4ms |
| `migrateProject`（zod 严格校验） | 10.7ms | **6.0ms** |
| `structuredClone`（存档拷贝） | 28.0ms | 146.8ms |

**结论：数据层合计约 240ms，差三秒太远。**两个此前的怀疑同时被证伪：
- **zod 不是元凶** —— 它随**字段节点数**增长，不随图片字节数增长（208 张图只让 zod 从 10.7ms 降到 6.0ms，纯噪声）；
- **`JSON.parse` 也不是** —— 70MB 只 89ms。

### 7.3 真因在渲染层：缩略图按原图分辨率解码

参考图面板里缩略图只显示 **56×56**，但把 `data:image/...` 直接挂 `src`，浏览器会按**原图分辨率完整解码**
（`loading="lazy"` 只能少解几张，免不掉）。改判据实测（`waitForMainThreadIdle` = 连续 400ms 无阻塞帧）：

| 口径 | 修复前 | 修复后 |
| --- | --- | --- |
| DOM 就绪（55.1MB 存档） | **3658ms** | **586~604ms**（三次复跑） |
| 主线程真正空闲 | 401ms | 402~571ms |
| 单次最长任务 | 376ms | 197~221ms |
| 长任务累计 | 453ms | 281~296ms |

对照**无图**用例：DOM 就绪稳定 438ms ——「加图前 438ms → 加图后 3658ms」的差值即图片解码成本。

### 7.4 修复（`src/App.tsx` 新增 `Thumb` 组件）

**做法：`IntersectionObserver`（`rootMargin: 240px`）只给近视口的图挂 `src`，其余保持空框**（CSS 已定 56×56，故延后挂载不产生布局位移）。

实测印证机制生效：12 个缩略图节点，**只解码了 2 张**（视口内的），其余 10 张延后 —— 这正是省下那 3 秒的来源。

**一处被自查拦下的错误实现（留痕）**：最初我给 `Thumb` 加了「`fetch(dataUrl)` → `URL.createObjectURL`（异步解码 + 按 URL 缓存）」。
写完核对 CSP 才发现行不通 —— `index.html` 的 CSP 是：

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; connect-src 'self' ws://127.0.0.1:*; object-src 'none'; base-uri 'self'
```

- `img-src` **不含 `blob:`** → object URL 挂上 `src` 会被拦；
- `connect-src` **不含 `data:`** → `fetch(dataUrl)` 同样会被拦；被拦后我那行 `.catch(() => setUrl(dataUrl))` 会**静默回退**成原样。

也就是说：那段代码在真实环境里**表面有收益、实际是空转**，属本项目明令反对的「静默失败」（收益本来就来自视口门控，与 URL 形态无关）。**已删除该分支，不扩大 CSP。**契约里也留了注释说明「`App.tsx` 第 44 行导出下载用的 `URL.createObjectURL` 与图片无关，不做全局否定断言」。

### 7.5 判据与护栏一起改

- e2e 新增 `waitForMainThreadIdle(page, quietMs, maxWait)`：用 `requestAnimationFrame` 帧间隔检测阻塞帧（间隔 > 25ms 即静默期重新计时），连续静默才算可交互。两条性能用例都改用它，并**同时打印**「DOM 就绪」与「主线程空闲」两个口径，让差距一眼可见。
- 「带参考图」用例新增 `expect(domReady).toBeLessThan(2500)` —— 基线约 600ms，回退到直挂 dataUrl 会立刻弹回 3600ms 量级，专门拦它。
- **新增「验产物」断言**（此前只有「节点存在」，属本项目明令反对的假绿）：用例改完后再取一次 DOM，断言**图片真的解码出来**（`img.complete && img.naturalWidth > 0`），并打印「N 个节点 / 已解码 M 张」。只验 `.image-item` 计数会漏掉「图根本没加载」—— 那同样会让 DOM 就绪很快。
- 文档契约新增防回流断言：`src/App.tsx` 必须含 `IntersectionObserver`、**不得**出现 `src={image.dataUrl}`、且必须含 `src={near ? dataUrl : undefined}`（正向锁住「进视口才挂」这个机制）；e2e 必须含 `waitForMainThreadIdle` 与 `naturalWidth`。

### 7.6 剩余未做（仍需老大批准）

- **A. 参考图与主存档分离**：图片单独一个 object store，主存档只留引用。收益 = 数据层从 240ms 降到约 20ms（打开）、每次自动保存的 `JSON.stringify` 从 250ms 降到约 11ms。**代价是存档结构变更 + 迁移兼容**，风险高于本轮改动，故未擅动。
